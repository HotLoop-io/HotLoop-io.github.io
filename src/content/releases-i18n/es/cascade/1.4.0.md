Si ejecuta Cascade en una planta, esta es la versión para el día después de instalarlo. Arranca limpia con una base de datos lenta, deja de crecer sin límite, y puede desmontarlo y volver a montarlo. El motor, el formato de archivo de los workflows, la API REST, el servidor MCP y los catorce idiomas son los de la 1.3.0.

## Qué cambió

- **Espera a su base de datos.** En la instalación dividida sobre PostgreSQL, los pods arrancaban antes de que el nombre de la base de datos se resolviera y se reiniciaban dos o tres veces. Ahora registran «waiting for the database» con el tiempo que llevan esperando y se conectan cuando responde. Una contraseña incorrecta o una base de datos que no existe siguen deteniéndolos de inmediato, porque esperar no arregla eso. Una instalación dividida nueva sobre un k3s real no mostró reinicios en tres ejecuciones.
- **Conservar las ejecuciones terminadas.** Un campo nuevo en Ajustes, Conservar las ejecuciones terminadas durante (días), viene desactivado, así que se conserva cada ejecución como antes. Indique un número y, una vez por hora, las ejecuciones correctas, fallidas y canceladas que terminaron hace más tiempo se eliminan junto con sus datos de pasos, y cada lote se escribe en el registro de auditoría. La misma pasada por hora ahora elimina las salidas grandes y los adjuntos a los que ninguna ejecución apunta, incluidos los que dejaron las ejecuciones que borró a mano, que antes se quedaban en disco para siempre.
- **Un límite para cada clave de API.** Un campo nuevo en Ajustes limita las peticiones por clave y por minuto, y viene desactivado. Las personas que han iniciado sesión en el editor no están sujetas a él. El recuento es el de cada proceso, así que con tres servidores una clave puede hacer hasta tres veces el número.
- **Copia de seguridad y restauración.** `hotloop-cascade backup` escribe una copia coherente de la base de datos SQLite mientras el servidor funciona, el archivo de clave, los archivos blob y un manifiesto con sus hashes. `hotloop-cascade restore` comprueba cada archivo contra el manifiesto y se niega a sobrescribir una base de datos o una clave distinta sin `--replace`. Con PostgreSQL guarda la clave, los blobs y el manifiesto, e imprime el comando `pg_dump` para la parte de la base de datos. Los blobs guardados en S3 o Azure no se copian.
- **La prueba de escala está hecha.** Dos servidores sobre un mismo PostgreSQL ejecutaron durante una hora un workflow que se dispara cada minuto mientras se mataba uno siete veces en el límite del turno: 61 ejecuciones para 61 turnos de minuto, ninguno perdido, ninguno duplicado.

## Actualización

Sin migraciones. `helm upgrade` a la 1.4.0, o deje que `:stable` actualice las unidades Quadlet. Volver a la 1.3.1 es seguro, porque nada cambió en la base de datos. Lo que una vuelta atrás no puede deshacer es una poda: las ejecuciones que la retención eliminó ya no están, y tampoco los blobs que eliminó la limpieza por hora. La retención está desactivada hasta que la active, así que haga antes una copia de seguridad. La limpieza de blobs funciona sin ella. Esta versión compila solo amd64, y la siguiente es el pequeño seguimiento que compila arm64.
