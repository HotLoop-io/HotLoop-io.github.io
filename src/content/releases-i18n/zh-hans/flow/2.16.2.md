HotLoop Flow 2.16.2 让大型流程运行起来很省资源。一家工厂运行 12,000 个节点，每秒约 3,000 条消息，没有人看仪表板，CPU 却已顶到上限。同一个流程现在只占约三分之一的 CPU 和不到一半的内存。您的流程、设置和 chart 都不会有任何变化。

## 变更内容

- **function 节点不再重复创建 JavaScript 运行时。** 每个 function 节点都保存着自己的一小池运行时，而 Go 的垃圾回收器在每个周期都会清空所有这些池。有几千个 function 节点的流程于是几乎为每条消息都创建一个新的运行时，由此产生的垃圾又触发下一次回收。12,000 个节点的流程的性能剖析显示，它 41% 的 CPU 花在这里。现在运行时来自一个回收器清不空的共享列表。全局对象被函数修改过的运行时会被丢弃，绝不会交给其他节点。
- **排队的一条消息占 24 字节，而不是 64 字节。** 每个节点的收件箱在节点启动时就按完整的 1,024 个位置分配，所以在 12,000 个节点的流程里，光收件箱就有约 800 MB 内存，回收器每个周期都要扫描一遍。现在约为 300 MB。
- **仪表板不再准备没人看得到的更新。** 没有打开页面时，仪表板每秒十次为每个变化的组件构建一份 JSON 更新，然后丢掉。现在它只清除变化，什么也不构建。之后打开的页面仍然从完整状态开始，数据点也包括在内。
- **一个留在测试套件里的负载测试。** 它构建一个与那家工厂形状相同的流程（烘干机标签页和记录器标签页各十一份，约 10,000 个运行中的节点，每秒约 2,900 条消息，没有客户端连接），保持 20 秒，如果每 1,000 条消息消耗超过 180 毫秒 CPU，或占用超过 520 MB 内存就会失败。预算按一个固定的空转循环缩放，所以较慢的机器不会吃亏。它在 2.16.1 上会失败。
- **Helm 索引保留所有已发布的版本。** 以前发布 chart 时，`index.yaml` 只根据新版本重建，所以固定在旧版 chart 上的客户在新版本发布后就无法重新渲染。现在它保留 Pages 上所有的版本。
- **浏览器测试每项检查最多等待 20 秒。** 在负载较重的运行器上，页面显示运行时发来的值要超过默认的 5 秒。这只改变测试。

## 它解决了什么，用数字说话

在一台机器上测得，同一个合成流程，每秒约 2,930 条消息，没有客户端连接：

| 指标 | 2.16.1 | 2.16.2 |
|---|---|---|
| 使用的 CPU | 0.79 核 | 0.29 核 |
| 每 1,000 条消息的 CPU | 268 ms | 99 ms |
| 空闲流程占用的内存 | 799 MB | 333 MB |

## 新设置

无。

## 升级

直接 `helm upgrade` 到 2.16.2 的镜像和 chart，或者在您的 Quadlet 单元里换成新标签。首次启动不会发生任何事，也不需要迁移。流程文件的加载和保存与以前逐字节一致。这个版本构建 amd64 镜像。`2.16` 和 `2` 标签保留它们从 2.16.1 就已有的 arm64 镜像，arm64 在 2.16.3 中回归。如果您用的是 arm64，请在那之前留在 2.16.1。

## 尚未证实的内容

这些数字来自一个按真实工厂形状构建的合成流程，其中 Modbus 读取用 inject 节点代替，PostgreSQL 记录器用 debug 节点代替。它们没有在那家工厂自己的流程上测过。在那家工厂的在线实例上，CPU 上升的同时内存也在持续增长（30 分钟约 200 MB），而合成流程保持平稳，所以我没有找到这种增长的来源，这个版本也不声称能制止它。修复后流程的性能剖析仍显示 function 节点占剩余 CPU 的一半左右，而为没人打开的页面转换每条消息的仪表板组件约占 7%。这些是接下来要做的。
