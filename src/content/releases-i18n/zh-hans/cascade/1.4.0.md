如果您在工厂里运行 Cascade，这是为安装之后的日子准备的版本。它在较慢的数据库上也能干净地启动，不再无限增长，您也可以把它拆开再装回去。引擎、workflow 文件格式、REST API、MCP 服务器和十四种语言都与 1.3.0 相同。

## 变更内容

- **它会等待数据库。** 在 PostgreSQL 上的拆分式安装中，pod 在数据库名称解析之前就启动，并重启两三次。现在它们会记录“waiting for the database”和已等待的时间，数据库一应答就连接。密码错误或数据库不存在仍会让它们立即停止，因为等待解决不了这些问题。在真实 k3s 上全新的拆分式安装，三次运行都没有重启。
- **保留已结束的运行记录。** 设置中新增字段 Keep finished runs for (days)，默认关闭，所以每次运行都像以前一样保留。填入一个数字后，每小时一次，结束时间早于该天数的成功、失败和已取消的运行会连同其步骤数据一起删除，每一批都会写入审计日志。这个每小时一次的清理现在还会删除没有任何运行指向的大型输出和附件，包括您手动删除的运行留下的那些，它们以前会永远留在磁盘上。
- **每个 API 密钥的上限。** 设置中新增的字段限制每个密钥每分钟的请求数，默认关闭。在编辑器中登录的人不受限制。计数按每个进程各自统计，所以有三台服务器时，一个密钥最多可以发出该数字的三倍。
- **备份和恢复。** `hotloop-cascade backup` 在服务器运行时写出 SQLite 数据库的一致副本、密钥文件、blob 文件和它们的哈希清单。`hotloop-cascade restore` 对照清单检查每个文件，没有 `--replace` 时拒绝覆盖数据库或不同的密钥。对于 PostgreSQL，它保存密钥、blob 和清单，并打印数据库那一半所用的 `pg_dump` 命令。保存在 S3 或 Azure 的 blob 不会被复制。
- **规模测试已完成。** 一个 PostgreSQL 上的两台服务器连续一小时运行每分钟触发的 workflow，期间其中一台在时间槽边界被终止七次：61 个一分钟时间槽对应 61 次运行，没有遗漏，没有重复。

## 升级

无迁移。对 1.4.0 执行 `helm upgrade`，或让 `:stable` 滚动更新 Quadlet 单元。退回 1.3.1 是安全的，因为数据库里没有任何改动。回退无法撤销的是清理：保留策略删除的运行记录已经没有了，每小时清理移除的 blob 也一样。保留策略在您开启之前是关闭的，所以请先做备份。blob 清理不需要它也会运行。此版本仅构建 amd64，其后的版本是构建 arm64 的小型后续版本。
