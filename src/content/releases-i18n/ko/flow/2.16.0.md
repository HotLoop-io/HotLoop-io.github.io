HotLoop Flow 2.16.0은 플로 파일 하나를 테넌트가 운영하는 모든 Flow 설치에 푸시하고, 두 설치가 하나의 작업을 나누되 한 번에 하나만 설비에 쓰게 합니다. amd64가 먼저 나오고 arm64는 2.16.1에서 뒤따릅니다.

## 새로운 점

- **테넌트의 스테이션에 푸시.** 플로 파일 하나가 FlowLab 다이어그램과 함께, EmberNet이 해당 테넌트에서 실행 중으로 표시하는 모든 Flow 설치에 한 번에 하나씩 전달됩니다. 배포할 때마다 스테이션은 모든 스테이션이 가져야 할 리비전으로 응답하고, 모든 노드를 시작하며, 다이어그램이 있고 실행 중이어야 합니다. 실패한 스테이션은 원래 있던 배포로 되돌려지고 푸시가 멈춥니다. 실행 중인 로거를 재시작하게 되는 푸시는 확인을 기다립니다.
- **fencing lease를 쓰는 웜 스탠바이.** 두 설치가 PostgreSQL의 lease 하나를 공유합니다. 설비에 쓰는 모든 동작이 먼저 이를 확인합니다. Modbus, S7, OPC UA, EtherNet/IP 쓰기 노드, HotLoop의 스크립트와 레시피 노드, FlowLab 다이어그램의 쓰기가 모두 해당됩니다. 스탠바이나 lease를 잃은 보유자는 아무것도 전송되기 전에 쓰기가 거부되고, 활성 설치의 lease가 끝나면 스탠바이가 넘겨받습니다.
- **같은 기능을 API와 MCP 도구로도** 제공하여 Flow 자체 도구가 44개가 되며, 둘 다를 위한 chart 값과 Quadlet 줄도 있습니다.

## 업그레이드

2.16.0 이미지와 chart로 평소처럼 `helm upgrade`를 하거나, Quadlet 유닛에 새 태그를 넣으면 됩니다. 처음 시작할 때 일어나는 일은 없고 마이그레이션할 것도 없습니다. 두 기능은 설정하기 전까지 꺼져 있으며, 플로 파일은 이전과 바이트 단위로 똑같이 불러오고 저장됩니다.

## 증명되지 않은 것

푸시는 랩 머신의 실제 Flow 설치들을 대상으로, 대시보드를 대신하는 대역을 써서 실행했으며, Flux를 거쳐 실제 테넌트로 보낸 것은 아닙니다. 스탠바이는 실제 PostgreSQL과 Modbus 서버를 상대로 실제 Flow 프로세스 두 개로 실행했고, 실제 PLC를 상대로 한 것은 아니므로, 설정값을 두 번 쓰면 PLC가 어떻게 반응하는지는 알 수 없습니다. 증분이 아니라 설정값을 쓰세요. lease 중에 데이터베이스 장애 조치는 시도하지 않았습니다. chart 값과 Quadlet 줄은 렌더링만 했고 클러스터에서 실행하지는 않았습니다.
