If you run Cascade for a plant, this is the release for the day after you installed it. It starts cleanly on a slow database, it stops growing without limit, and you can take it apart and put it back. The engine, the workflow file format, the REST API, the MCP server and the fourteen languages are what 1.3.0 had.

## What changed

- **It waits for its database.** In the split install on PostgreSQL the pods used to start before the database's name resolved and restart two or three times. They now log "waiting for the database" with how long they have waited and connect when it answers. A wrong password or a database that does not exist still stops them at once, because waiting cannot fix those. A fresh split install on a real k3s showed no restarts in three runs.
- **Keeping finished runs.** A new Settings field, Keep finished runs for (days), is off by default, so every run is kept as before. Set a number and once an hour the succeeded, failed and canceled runs that ended longer ago than that are deleted with their step data, and each batch is written to the audit log. The same hourly pass now removes big outputs and attachments that no run points at, including those left by runs you deleted by hand, which used to stay on disk for good.
- **A limit for each API key.** A new Settings field caps requests per key per minute, off by default. People signed in to the editor are not held to it. The count is each process's own, so with three servers a key can make up to three times the number.
- **Backup and restore.** `hotloop-cascade backup` writes a consistent copy of the SQLite database while the server runs, the key file, the blob files and a manifest of their hashes. `hotloop-cascade restore` checks every file against the manifest and refuses to overwrite a database or a different key without `--replace`. For PostgreSQL it holds the key, blobs and manifest and prints the `pg_dump` command for the database's half. Blobs kept in S3 or Azure are not copied.
- **The scale test is done.** Two servers on one PostgreSQL ran a workflow that fires every minute for an hour while one was killed seven times at the slot boundary: 61 runs for 61 minute slots, none missed, none doubled.

## Upgrade

No migrations. `helm upgrade` to 1.4.0, or let `:stable` roll the Quadlet units. Putting 1.3.1 back is safe, because nothing in the database changed. What a rollback cannot undo is a prune: runs that retention deleted are gone, and so are the blobs the hourly cleanup removed. Retention is off until you turn it on, so take a backup first. The blob cleanup runs without it. This release builds amd64 only, and the release after it is the one small bump that builds arm64.

## What isn't proven

- The update path was tried against a local registry standing in for ghcr.io, not ghcr.io itself.
- The chart and Quadlet runs and the hour of killing a server were done on the release candidate, which differs from 1.4.0 by a log back-off fix, a language check and the version strings. The full suite ran again on the 1.4.0 commit.
- No native speaker has reviewed the translations.
