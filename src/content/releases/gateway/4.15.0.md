summary: "The OPC UA driver can log in to a secured server, which is to say most of the ones in production."
highlights:
  - "The driver used to send an empty identity token policy, which a compliant server refuses in every mode, including the Gateway's own OPC UA server. It now asks the server for its endpoints, picks the one matching the device's security mode and policy, and uses the policy id that endpoint lists."
  - "Basic256Sha256, Aes128_Sha256_RsaOaep, and Aes256_Sha256_RsaPss, in Sign or SignAndEncrypt. The deprecated Basic128Rsa15 and Basic256 are never picked, even when a server offers nothing else."
  - "The server's certificate has to be approved by an operator before anything is sent to it. An unknown certificate is saved for approval and the connection fails with a message saying exactly how."
  - "A password is refused before it is sent unless the channel is secured and something encrypts it. That includes a user name over an unsecured channel whose token policy claims to encrypt the password, because the key comes from a reply nothing authenticates."
  - "A refused login waits ten minutes before trying again, so a wrong password cannot lock an account or eat the server's sessions."
breaking: []

Tested against the Gateway's own OPC UA server and Microsoft's opc-plc. Aes256_Sha256_RsaPss failed against opc-plc, so the driver only uses it when a device asks for it by name. In this version the API still returned the MQTT, HTTP, and MTConnect passwords in the clear. 4.15.1 fixed that.
