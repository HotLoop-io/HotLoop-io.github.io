HotLoop Flow 2.16.0 pushes one flow file to every Flow install a tenant runs, and lets two installs share one job with only one of them writing to equipment at a time. It is amd64 first, with arm64 following in 2.16.1.

## What's new

- **Push to a tenant's stations.** A flow file, with its FlowLab diagrams, goes to each Flow install EmberNet shows as running for the tenant, one at a time. After each deploy the station has to answer the revision every station is to have, start every node, and have its diagrams present and running. A station that fails is put back to the deployment it was on and the push stops. A push that would restart a running logger waits for a yes.
- **A warm standby with a fencing lease.** Two installs share one lease in a PostgreSQL. Every write to equipment checks it first, in the Modbus, S7, OPC UA and EtherNet/IP write nodes, the HotLoop script and recipe nodes, and the FlowLab diagram writes. A standby, or a holder that lost its lease, has its write refused before anything is sent, and the standby takes over after the active one's lease runs out.
- **The same over the API and as MCP tools,** which brings Flow's own tools to 44, and chart values and Quadlet lines for both.

## Upgrade

A plain `helm upgrade` to the 2.16.0 image and chart, or the new tag in your Quadlet unit. Nothing happens on first start and nothing needs migrating. Both features are off until you set them up, and a flow file loads and saves byte for byte as before.

## What isn't proven

The push was run against real Flow installs on a lab box, with a stand-in for the dashboard, and not through Flux to a real tenant. The standby was run as two real Flow processes against a real PostgreSQL and a Modbus server, and not against a real PLC, so what one does with a setpoint written twice is not known: write setpoints, not increments. A database failover under the lease was not tried. The chart values and Quadlet lines were rendered and not run on a cluster.
